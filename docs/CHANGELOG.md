## 0.13.0 — layer 3: the pill becomes the control surface (operator doctrine, decision 2543834f)

- **byebyted could not start under its own systemd unit from v0.8.0 through this release** (70fd9c2, found in alfred's pre-tag review of the published v0.12.0 `.deb`, DM #3082): `byebyted.service`'s `SystemCallFilter` never allowlisted `fanotify_init`/`fanotify_mark`, which the burn-path attribution added in v0.8.0 calls unconditionally at startup — a syscall outside the filter is `SIGSYS`, the kernel kills the process outright, not a graceful `EPERM` the code's own degrade path could catch. CI never caught it because it runs the daemon directly, never under the real unit. Two more real defects found the same pass and fixed alongside it: the `.deb`'s three `.service` units all pointed `ExecStart` at `/usr/local/bin` while the `.deb` installs to `/usr/bin`; `byebyte --help`/`-h` fell through to a live `status` call instead of printing usage. All three verified against a real systemd 259 container, including a negative control that reproduced the exact crash before confirming the fix. This is the first byebyte release that actually runs as installed, not just as developed against.

- **layer 3, the family's own product doctrine** ("the point of the pills is to turn linux bullshit into a pill" — operator, verbatim; the pill is the control surface, the CLI is for agents and experts): five new verbs, each with a verified affordance/cost/risk/undo shape —
  - `declare <path>`: path-exact destructive reclaim, scope named by the user, never inferred from a category
  - `reserve <mountpoint> <percent>`: ext2/3/4 reserved-blocks via `tune2fs -m`
  - `journal-cap <size>`: bounds journald's own persistent footprint via a `journald.conf.d` drop-in, applied live
  - `fstrim-schedule <on|off>`: the stock weekly TRIM timer's own enablement, immediate
  - `tmp-size <size>`: caps `/tmp`'s tmpfs via a `tmp.mount` drop-in — PENDING by design (see below), the family's first verb whose write is instant but whose effect waits for a remount

- **the pill grows a matching control surface**: a Reclaim ▸ pick-list for `declare`, a SEGMENT chip strip for `reserve`, then a second wave — SEGMENT strips for `journal-cap`/`tmp-size` and a TOGGLE for `fstrim-schedule` — built against a new `build_pill_summary()` digest embedded in `status.json` (porting ramstein's own shape, so the pill reads current state from the file it already watches instead of growing its own socket client). All five layer-3 verbs are now reachable from the pill, not just the CLI.

- **PENDING, a new affordance (decision 3b31bc10) for verbs whose write is instant but whose effect isn't**: `tmp-size`'s response and its pill row both render the CONFIGURED cap and the EFFECTIVE live size side by side whenever they diverge (`/tmp: 24G now — 8G after reboot`), and never claim the effective size has changed until it genuinely has. Caught and fixed before shipping: the first implementation compared configured-vs-effective by non-null rather than requiring both sides to be comparable numbers, which would have rendered a false PENDING on every untouched machine — Ubuntu/Debian's own stock `tmp.mount` defaults `size=` to a percentage, unparseable as an absolute byte count, and non-null alone can't tell "never configured" from "configured as something that can't be compared."

- **the `.deb`'s control stanza now actually emits the `Suggests` tier its own `packages.txt` had documented for months** (operator ruling 2cd900ce, the same gap found in byebyte and RAMstein both that night): `btrfs-progs`, `snapd`, `libnotify-bin`, `gnome-shell` ride as `Suggests`, never `Recommends`. Every optional-dependency refusal now names the fix (`apt install <package>`) instead of just stating the fact. `packaging/packages.txt` reformatted to conform to sutra.mk's own generator/verifier spec once it landed, catching two real conformance gaps of its own first — a multi-line section header the spec's parser would never have recognized, and a missing version constraint on `python3` — before the verifier would have.

- **spelled consistently, lowercase, throughout** (operator ruling): `ByeByte` → `byebyte`, and once the operator renamed the sibling repo, `RAMstein` → `ramstein` — every prose/comment/doc/URL reference this repo owns, including this changelog's own history. The four vendored sutra files are deliberately exempt (sha256-checked byte-for-byte against canonical; hand-editing them would be indistinguishable from corruption) — re-vendored separately below instead.

- **re-vendored sutra 0.11.1 → 0.12.9** (canonical `db9ec14`): closes the LAG `check-sutra` had been reporting and finishes the spelling sweep in the one place it couldn't reach directly. `sutra.py`/`sutra_xen.py`/`sutra_update.py` are name-and-version-only diffs, confirmed line by line; `sutra.mk` carries a real functional change alongside the rename (a removed default that now fails loud instead of silently, a dash-quoting fix, and a new opt-in `check-packages` target implementing the same generator spec `packages.txt` now conforms to).

- **hardening found and fixed in this same arc, none pre-existing in a released tag**: `attack_socket.py` leaked ~2.1G of RAM per run via an uncleaned runtime dir; the index never walked into tmpfs mounts, leaving `why`/`blame` blind to them; a purge/sweep/declare candidate could be revalidated once at detect-time and deleted seconds (or, for the unbounded `project-artifacts` walk, minutes) later against a target that had since changed underneath it (5f81f00, fixed with an immediate pre-delete revalidation, proven against a genuine cross-device root); `sweep`'s own unbounded `project-artifacts` walk cost 169.83s on every unarmed preview even though `advise()` already knew to skip it (3e9e5fa); `request_or_die()` swallowed every verb's own `--json` error body behind a bare exit code.

- **verified throughout**: `make check`/`smoke`/`attack` green at every step above; CI (`systemd-unit` — a real `.deb` installed and polled to completion under an actual systemd, not just the raw binary — plus the shared static/smoke/attack suite) green on every commit in this arc before it landed.

- **not yet installed**: the pill running on the operator's own machine was still the pre-layer-3 build until this release — most of the work above reaches a real user for the first time here.

## 0.9.0 — V2.M4: sweep (the unattended reclaim policy)
- byebyted: `sweep(force_dry, cfg, indexer)` — double-consent unattended reclaim per docs/V2-SPEC.md M4 and UNIFY.md's ledger/notification specs. Consent #1 is the new `byebyte-sweep.timer` (disabled by default); consent #2 is the new `sweep_categories` config key (list of REGISTRY category ids to arm — validated as a subset, config can never widen beyond the compiled-in registry, same invariant `purge_disabled` already established in the other direction)
- an unarmed category, or the whole call under `--dry`, only ever previews: reports what it would reclaim and ledgers a `dry_run` entry (only when there's something to report, to keep the ledger from filling with empty "nothing found" lines every timer tick), never touches disk. Armed categories reuse purge's own compiled-in detect/delete functions verbatim to actually reclaim, ledgering `sweep:<category>` per act
- kernels stay report-only, unconditionally, even if named in `sweep_categories` (validated away): `kernels()` carries M3's own "never runs apt" invariant, and unattended kernel removal is a materially different, higher-stakes capability that needs its own explicit authorization — not bundled silently into this milestone. Ghosts (kill-after-confirm) and ballast (expiry) aren't reclaim categories here at all yet, for the same reason — no policy classifier or expiry definition has been ruled on; flagged to alfred rather than guessed

## 0.8.4 — fix: make deb race condition (0.8.3's fix wasn't the root cause)
- 0.8.3's lintian hardening was correct but didn't fix alfred's actual bug: he forensically boxed an impossible paradox (`make deb` returns rc=1, yet its captured log shows complete success, and a mysterious level-1 sub-make "Leaving directory" line appears despite smoke.sh having exactly one make call)
- real root cause: `DEBROOT`/`DEBFILE` (the deb staging directory and the smoke-test log path) were FIXED, non-unique paths — `build/deb/byebyte_<version>_all[.deb]` and `/tmp/byebyte-deb-build.log`. This dev box runs concurrent smoke passes constantly (root and unprivileged, different agents, same checkout); two concurrent `make deb` invocations racing on the same staging directory and log file produces exactly alfred's paradox — one process's real failure, with the OTHER (successful) process's clean output clobbering the shared log by the time anyone reads it
- reproduced directly: a leftover ROOT-owned staging directory from a prior privileged run permission-denied every file in an unprivileged `rm -rf` of the same fixed path — the exact class of cross-run interference this predicts
- fix: `DEBROOT` is now per-invocation-unique (random suffix); the final `DEBFILE` name stays canonical (it's the real release artifact name) but is only ever populated via an atomic `mv` from a per-invocation temp build target, so concurrent builds can never leave it torn; smoke.sh's log path is now `mktemp`-unique instead of fixed, and its `DEBFILE` lookup is now deterministic (derived from VERSION, matching the Makefile) instead of an ambiguous "most recently modified" glob

## 0.8.3 — fix: silent `make deb` failure under root
